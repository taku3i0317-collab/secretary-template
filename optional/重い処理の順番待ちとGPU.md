# 重い処理の順番待ちと、グラボ（GPU）の使い分け

何本もの作業場（別の会話）が、同じ PC で重い処理（3D の描き出し・学習・動画の書き出し・全件の検査）を同時に始めると、PC が固まる・画面が乱れる・どれも遅くなる。`heavy_slot.py` は、重い処理を**順番待ちの列に並べて、空きに合わせて始める**小さな道具（Python 3 だけで動く）。作業場が1つだけ、または重い処理をしないなら要らない。

## 使い方
```
python optional/heavy_slot.py run --name 作業名 -- <重いコマンド>
python optional/heavy_slot.py run --name 作業名 --device cpu --mem 4 -- <コマンド>
python optional/heavy_slot.py status
```
- 重い処理を始めるときは、必ずこれを通す、と作業場の `CLAUDE.md` に書く（秘書のフォルダではなく、作業場側）
- 枠の数・余裕は `~/.heavy_slot/config.json`（環境変数 `HEAVY_SLOT_BASE` で場所を変えられる）。無ければ `heavy_slot.py` の上の DEFAULT。自分の PC に合わせて直す

## 考え方（4つ）
1. **枠の数に上限**：グラボの枠・CPU の枠・全部で何本まで、を決める。グラボを2本が同時に使うと、どちらも遅く、メモリ不足で落ちやすい。まず1〜2本から
2. **スレッドは「空き」に合わせる**：始めるとき、全スレッド − 画面用に残す分 − 今使われている分 を、その仕事に渡す。今使われている分は、①今の CPU 使用率から出した数 ②動いている重い処理に渡した数の合計、の**大きい方**（片方だけだと、重い処理以外が使っている分や、まだ使い始めていない分を見落とす）
3. **画面の余裕を残す**：空きメモリ・空き VRAM が「この仕事の見込み ＋ 画面用の分」に足りなければ始めない。足りない理由は画面に出す（「待つ: 空きメモリが足りない…」）。大きい仕事が入らないとき、後ろの小さい仕事は先に入れる
4. **待ちは列から落ちない**：待ちは `wait/<PID>.json` の札で数える。札が消されても、同じ順番で列に戻る。持ち主のプロセスが死んでいる枠・札は空きとみなして片付ける（PID の使い回しは、プロセスの作られた時刻で見分ける）。書きかけのファイルを読まれないよう、写しに書いてから入れ替える

## グラボ（GPU）の使い分け
| 処理 | 置き場所 | 理由 |
|---|---|---|
| 3D の描き出し・焼き付け、学習、動画の書き出し | グラボの枠（`--device gpu`） | グラボが速い。ただし VRAM を食うので、同時は1〜2本 |
| 毛・布のシミュレーション、全コマの検査、データ整理 | CPU の枠（`--device cpu`） | グラボを使わない。グラボの枠を空けておける |
| どちらでもよい | `--device any` | グラボの枠が空いていればそちら、無ければ CPU |

- **使う側のプログラムは、渡された環境変数に従う**：`HEAVY_SLOT_DEVICE`（`gpu` か `cpu`）で装置を決め、`HEAVY_SLOT_THREADS` でスレッド数を決める（`OMP_NUM_THREADS` 等も同じ値で渡してある）。枠は CPU なのにグラボを使うと、枠の数えが狂う
- 実際に使えた装置は、使う側が記録に残す（グラボが見つからず CPU に落ちたのに気づけないと、遅い理由が分からない）
- グラボのメモリを見るのに `nvidia-smi` を使う。無い PC（グラボが違う・無い）では VRAM の確認は飛ばす
- すぐ終わる軽い処理（1〜2枚の画面確認など）は枠を通さなくてよい
- 10 秒より早く 0 以外で終わった処理は、コマンドの書き方が間違っていることが多い。終了コードを見る

## Windows の注意
- `bash` を渡すと WSL の bash が起動して、パスが合わず失敗することがある。シェルを通さず、実行ファイルを直接渡すのが基本（シェルが要るときは Git Bash のフルパスを渡す）
- 子の処理は、優先度を下げて起動する（画面・操作を先にする）。Windows 以外ではそのまま起動する
